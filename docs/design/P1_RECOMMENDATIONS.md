# P1. «Что посмотрим» с рекомендациями — дизайн-док

Статус: **черновик, ждёт ОК владельца** (30.10.2026). Код — отдельным PR
после ОК. Пункт — `docs/BACKLOG.md`, раздел «На обсуждение», P1.

## 1. Проблема

Колода «Что посмотрим» пуста, пока кто-то из пары не добавит фильм руками
через поиск. Свайпать нечего, совпадений мало, экран открывают и закрывают.
Хотим:

1. С первого запуска — колода из **перемешанного топ-1000** фильмов и
   сериалов.
2. После **N совпадений** — колода подстраивается под вкус пары: сначала то,
   что скорее понравится обоим.
3. Ручное добавление через поиск остаётся как есть.

Ограничение, которое определяет всё остальное: сервер не видит содержимое
пары (`docs/E2E.md` §1, §4, дополнение 2026-10-23 «шифровать всё»). Что
пара лайкнула — это содержимое, его серверу знать нельзя.

## 2. Как сейчас

**Клиент.**

- `lib/fork/movies/movie_swipes.dart` — экран `ForkMovieSwipesScreen`, три
  вкладки: «Выбор» (свайп карточки, D4), «Добавить» (поиск), «Совпало · n».
  Открывается из `lib/screens/together/watch_home_screen.dart`.
- `lib/fork/movies/movie_choices.dart`:
  - `ForkMovieCard` — карточка: `id` (номер Кинопоиска или 0), название,
    оригинал, год, вид, жанры строкой, описание, постер (https), ссылка
    (только kinopoisk.ru / imdb.com / wikidata.org). Ключ карточки
    `key`: `kp:<id>`, иначе `url:<ссылка>`, иначе `title:[…]`.
  - `ForkMovieChoice` — одна запись на (пара, человек, фильм): `state` с
    карточкой и голосом `0` — предложил, `1` — да, `2` — нет (одна цифра,
    чтобы длина шифра не выдавала голос).
  - `ForkMoviePicks` — сводка: `pending` (я не голосовал), `matches` (оба
    «да»). Колода «Выбор» = `pending` в порядке первого появления.
  - `ForkMovieChoices` — репозиторий поверх PocketBase: `list`, `propose`,
    `vote`, `watch` (дельты канала `pair:<group>` + переподключение).
- Поиск — `lib/services/movie_search_service.dart` → сервер
  `/api/movies/search`; запасной путь — poiskkino со своим ключом сборки.

**Сервер (Go).**

- Коллекция `fork_movie_choices` (`server/internal/migrations/movie_choices.go`):
  открыто `group_id`, `author_uid`, `movie_tag` (keyed hash ключом пары от
  `movie-choice-v1/<group>/<key>`), шифром — `state`. Уникальный индекс
  `(group_id, author_uid, movie_tag)`. Правила — `privateLiveAuthored`
  (`domain/access/rules.go`), дельты в канал пары (`domain/realtime/channels.go`),
  удаление вместе с аккаунтом (`usecase/account/account.go`).
- Поиск — `server/internal/usecase/movies/movies.go` + `domain/movies`:
  Викиданные первыми (без ключа, CC0), poiskkino — только если оператор
  задал свой ключ. Ответ ужимается до карточки в форме poiskkino. Кэш —
  LRU в памяти (`cache.go`), после рестарта пустой.
- В комментарии к `movie_search_service.dart` уже зафиксировано решение
  19.09.2026: общий ключ poiskkino выгорал (бесплатно — 200 запросов в
  сутки), TMDB — некоммерческая лицензия, поэтому Викиданные.

**Что сервер видит сейчас:** что в паре кто-то проголосовал (запись,
время, автор), число записей. Какой фильм и какой голос — нет: метка —
hash с ключом пары, `state` — шифр.

## 3. Источник топ-1000

Нужно: ~1000–1500 популярных фильмов/сериалов/мультфильмов/аниме с
названием на языках приложения (`dm.Langs`: ru, en, de, fr, es, it, pt, zh),
годом, жанрами, постером и признаками для вкуса (жанр, страна, режиссёр,
язык, десятилетие).

### 3.1 Викиданные (Wikidata Query Service, SPARQL)

- **Лицензия:** структурные данные Викиданных — CC0, без условий об
  атрибуции и некоммерческом использовании
  ([Wikidata:Licensing](https://www.wikidata.org/wiki/Wikidata:Licensing)).
  Значит, каталог можно класть в репозиторий (GPL-3.0) и в APK.
- **Ключ:** не нужен. Нужен узнаваемый `User-Agent` — у нас он уже есть
  (`Options.UserAgent`); клиентов без него WDQS блокирует
  ([WDQS User Manual](https://www.mediawiki.org/wiki/Wikidata_Query_Service/User_Manual#Query_limits)).
- **Лимиты WDQS:** жёсткий таймаут запроса 60 с, 60 с процессорного времени
  в минуту на клиента (User-Agent + IP), до 30 ошибочных запросов в минуту
  (там же). Для разовой сборки каталога этого хватает, если вытаскивать
  страницами по классам (фильм, сериал, аниме…).
- **«Топ» — чем мерить:** рейтингов зрителей в Викиданных нет (свойство
  `P444` «оценка» заполнено редко и неоднородно). Рабочая мера
  популярности — **число статей в Википедиях** (`wikibase:sitelinks`): чем
  на большем числе языков есть статья, тем известнее фильм. Это прокси, не
  «лучшие по оценкам»: тянет к классике и блокбастерам, свежие фильмы
  отстают на месяцы.
- **Постеры:** у многих записей есть номер Кинопоиска (`P2603`) — тогда
  постер и ссылка, как сейчас в `DocFromCompact`
  (`st.kp.yandex.net/…/iphone360_<id>.jpg`, хотлинк, мы его не храним).
  Иначе — файл на Commons (`P3383`), но постеры обычно несвободны и на
  Commons их мало; без постера — заглушка с названием.
- **Признаки для вкуса:** жанр `P136` (таблица `genreOf` уже есть), страна
  `P495`, режиссёр `P57`, язык оригинала `P364`, год `P577`/`P580`, вид
  `P31`. Всё — открытые факты о фильме, не о паре.
- **Кэш и офлайн:** каталог собирается **заранее** и лежит файлом —
  офлайн работает с первого запуска, WDQS в рантайме не нужен.

### 3.2 TMDB

- **Лицензия:** бесплатный ключ — только некоммерческое использование;
  коммерческое — отдельный договор, возможно платный
  ([API Terms of Use](https://www.themoviedb.org/api-terms-of-use),
  [FAQ](https://developer.themoviedb.org/docs/faq)). «Коммерческий» по FAQ —
  если основная цель проекта — доход владельца.
- **Атрибуция:** обязательны одобренный логотип TMDB и строка «This product
  uses the TMDB API but is not endorsed or certified by TMDB», логотип —
  менее заметный, чем знак приложения ([FAQ](https://developer.themoviedb.org/docs/faq)).
- **Кэш:** запрещено хранить полученное от TMDB дольше 6 месяцев; при
  прекращении лицензии — удалить, включая кэш
  ([API Terms of Use](https://www.themoviedb.org/api-terms-of-use)).
  Положить снимок в репозиторий/APK навсегда — противоречит этому пункту.
- **Ключ:** в APK открытого проекта ключ становится публичным; значит, ходить
  в TMDB должен сервер, ключ — у оператора (как у poiskkino).
- **Плюсы:** лучшие данные (top_rated/popular, постеры, `similar` и
  `recommendations`). **Минусы:** лицензия зависит от того, коммерческий ли
  проект (вопрос владельцу, §12); каталог нельзя заморозить; `similar` по
  лайкнутым фильмам означает отдать серверу и TMDB вкус пары — против E2E.

> Примечание: из среды, где писался документ, сайты TMDB, IMDb и Викиданных
> не открывались напрямую; условия сверены по поисковой выдаче с цитатами
> официальных страниц. Перед реализацией с TMDB — перечитать живые условия.

### 3.3 Прочие

| Источник | Лицензия | Годится? |
|---|---|---|
| poiskkino.dev (неофиц. API Кинопоиска) | ключ; бесплатный тариф 200 запросов/сутки (наш опыт 19.09, `movie_search_service.dart`); условия на распространение данных не проверял | Нет: лимит, каталог в APK класть нельзя без явного разрешения. Остаётся запасным путём поиска |
| IMDb Non-Commercial Datasets (`title.ratings.tsv` и др.) | только личное некоммерческое использование, нельзя переиздавать и делать из них базу ([IMDb](https://developer.imdb.com/non-commercial-datasets/), [Help](https://help.imdb.com/article/imdb/general-information/can-i-use-imdb-data-in-my-software/G5JTRESSHJBBHTGX)) | Нет: класть в репозиторий/APK = переиздавать |
| MovieLens (оценки пользователей) | без отдельного разрешения GroupLens — нельзя распространять и использовать в коммерческих целях; у разных версий условия различаются ([README ml-100k](https://files.grouplens.org/datasets/movielens/ml-100k-README.txt)) | Нет для каталога. Для «похожих» по чужим оценкам — только с письменным разрешением |

**Итог по источнику:** Викиданные. Единственный вариант, который можно
заморозить в файл, положить в репозиторий и APK, не держать ключ и не
спрашивать сеть при каждом свайпе.

## 4. Где считается вкус

| | А. Клиент | Б. Go-сервер | В. Сервер «вслепую» |
|---|---|---|---|
| Как | Каталог с признаками — на телефоне; голоса пары уже там (расшифрованы); скоринг — чистая функция Dart | Клиент шлёт серверу лайки/дизлайки, сервер считает и отдаёт подборку | Клиент скачивает весь каталог или его страницы в одном для всех порядке, сервер не знает, что выбрано |
| E2E | Ничего нового серверу не уходит | **Нарушает**: вкус пары = содержимое, серверу виден в момент запроса (даже без хранения) | Ок, но это и есть вариант А с другой раздачей файла |
| Офлайн | Работает | Нет | Как А |
| Сложность | Скоринг на 1–2 тыс. фильмов — миллисекунды | Новый эндпоинт, кэш, лимиты | Как А |
| Чужие пары (collaborative filtering) | Нет | Возможно, но это сбор вкусов всех пар — против E2E | Нет |

**Совместимость пары.** Оба телефона видят одни и те же записи (свои и
партнёра) и один каталог. Если скоринг детерминирован, оба получают **одну и
ту же** колоду в одном порядке — это нужно, чтобы совпадения случались, а
не разъезжались по разным фильмам. Перемешивание до порога — тоже
детерминированное: зерно — keyed hash ключом пары от
`movie-deck-v1/<group>` (как `movie_tag`). Сервер зерна не знает, у пары —
одно и то же.

Вывод: **вкус считает клиент (А)**. Go-серверу достаётся только раздача
публичного каталога (если решим обновлять его не только с релизами).

## 5. Модель вкуса

Без чужих данных — только контентная модель по признакам фильма.

1. **Признаки** карточки каталога: жанры (до 3), вид (`movie`, `tv-series`,
   `cartoon`, `anime`…), десятилетие, страна, язык оригинала, режиссёр.
2. **Вес признака для человека** `u`: по его голосам «да»/«нет»
   `w_u(f) = (да_f − нет_f) / (да_f + нет_f + 2)` — сглаживание, чтобы один
   голос не решал всё.
3. **Оценка фильма для человека:** взвешенное среднее `w_u` по признакам
   фильма (жанр 1.0, режиссёр 0.8, вид 0.6, десятилетие 0.4, страна 0.3,
   язык 0.3) + малая добавка популярности (ранг в каталоге).
4. **Оценка для пары:** `min(score_я, score_партнёр)` + бонус за признаки
   совпавших фильмов. `min`, а не среднее: цель — совпадение, фильм должен
   зайти обоим.
5. **Порядок колоды:**
   - сначала фильмы, где партнёр сказал «да», а я ещё нет (как сейчас
     `pending`, но с приоритетом — это ближайшие совпадения);
   - ручные предложения партнёра;
   - затем каталог без проголосованных: после порога — по оценке пары с
     долей **разведки** (каждая 4-я карточка — из перемешанного остатка),
     до порога — только перемешанный каталог.
6. **Объяснение** на карточке подборки: «похоже на «X»» — совпавший фильм с
   наибольшим пересечением признаков, или «вы оба любите комедии».

Голоса за фильмы, добавленные руками и отсутствующие в каталоге, тоже
учитываются: признаки у них — жанры и вид из карточки (остальных нет).

## 6. Порог N

- **N = 5 совпадений** и не меньше **20 голосов у каждого**. Пять «оба да» —
  уже видны общие жанры; 20 голосов на человека дают и «нет», без которых
  вес признака однобокий.
- Не рубильник, а плавный вход: доля подборки растёт от 0 % на пороге до
  75 % (остальное — разведка) к 3N совпадениям.
- N — константа в коде (`kMovieTasteThreshold`), не настройка в UI.
- До порога на «Выборе» — строка прогресса: «Ещё 3 совпадения — и колода
  начнёт подстраиваться под вас».

## 7. Хранение

| Что | Где | Почему |
|---|---|---|
| Каталог (~1500 записей) | **asset в APK**: `assets/fork/movies/catalog.json.gz`, версия в файле | Публичные CC0-данные, одинаковы для всех; офлайн с первого запуска |
| Обновление каталога | Вариант 1 (рекоменд.): только с релизом. Вариант 2: Go отдаёт `GET /api/fork/movies/catalog?v=` — тот же файл для всех, клиент кэширует | Вариант 2 серверу ничего не говорит о паре, но это ещё эндпоинт; решает владелец (§12) |
| Сборка каталога | скрипт `tool/fork/build_movie_catalog.*` (SPARQL к WDQS → ужатие → gzip), запускается руками перед релизом; результат коммитится | Воспроизводимо, без WDQS в рантайме |
| Голоса | без изменений — `fork_movie_choices`, `state` шифром | Новая коллекция не нужна; карточка каталога ложится в `ForkMovieCard` |
| Модель вкуса | не храним, пересчитываем из голосов при открытии экрана | Голосов сотни, считать дешевле, чем синхронизировать ещё одну запись |
| Позиция в колоде | не храним: «первый непроголосованный» в детерминированном порядке | |

**Размер.** На запись: id Кинопоиска, QID, ярлыки на 8 языках, год, вид,
коды жанров/страны/языка, QID режиссёра — порядка 400–600 байт в JSON,
1500 записей ≈ 0,7–0,9 МБ, в gzip примерно втрое меньше. Оценка, проверить
на сборке.

**Ключ карточки.** Каталог и поиск идут из одного источника (Викиданные),
поэтому фильм из каталога и тот же фильм из поиска получают один ключ
(`kp:<id>` или `url:<imdb/wikidata>`) и не двоятся в колоде.

**Что видит сервер после P1:** то же, что сейчас (§2). Записей станет
больше — они появляются только при голосе, а не при показе карточки.
Голос «нет» за фильм из каталога тоже создаёт запись — иначе после
переустановки он вернётся в колоду; это метаданные «сколько свайпов»,
уже открытые сейчас.

## 8. Офлайн

- Каталог и скоринг — офлайн.
- Голос сейчас идёт онлайн (`_write` читает `list` перед записью). Офлайн-
  очередь для голосов — отдельный вопрос, в P1 не входит; без сети карточка
  возвращается с ошибкой «повторить», как сейчас.

## 9. Сравнение вариантов

| Вариант | Лицензия | E2E | Офлайн | Качество подборки | Работы |
|---|---|---|---|---|---|
| **1. Викиданные → asset, вкус на клиенте** | CC0, чисто | Ничего нового | Да | Средняя (контентная, «топ» по sitelinks) | Скрипт + Dart-скоринг + экран |
| 2. Викиданные → Go-эндпоинт каталога, вкус на клиенте | CC0 | Ничего нового | После первой загрузки | Как 1, свежее | + эндпоинт и кэш |
| 3. TMDB через Go, `similar` по лайкам | некоммерч., атрибуция, кэш ≤ 6 мес. | **Нарушает** | Нет | Высокая | Ключ у оператора, эндпоинт, логотип |
| 4. TMDB только для каталога, вкус на клиенте | некоммерч.; снимок в APK конфликтует с 6 мес. | Ок | Пока свежий | Выше (top_rated) | Регулярная пересборка, атрибуция |

## 10. Рекомендация

**Вариант 1**, с заделом на 2:

1. Скрипт сборки каталога из Викиданных (CC0): ~1500 записей, квоты по видам
   (например, 900 фильмов, 300 сериалов, 150 мультфильмов, 150 аниме),
   популярность — sitelinks, без `Q185529` (как `Adult` в `domain/movies`).
2. Каталог — asset; обновляем с релизами.
3. Колода: детерминированное перемешивание с зерном от ключа пары → после
   N = 5 совпадений — подборка по контентной модели (§5) с разведкой 25 %.
4. Вкус — только на клиенте, чистая функция с тестами; сервер не меняется.
5. «Добавить» — без изменений.

План PR после ОК: (а) скрипт + каталог + загрузчик; (б) колода из каталога
с перемешиванием; (в) модель вкуса и порог; (г) строка прогресса и
объяснение «похоже на». Стражи: детерминизм порядка на двух «телефонах»
(одни записи → одна колода), отсутствие сетевых вызовов в скоринге, каталог
без `Adult`.

Карточка разведки — без «✦ Подборка». Колода кончилась — «Каталог
пройден: добавьте свои фильмы во вкладке „Добавить“».

**Фильтр видов** (фильмы / сериалы / мультфильмы / аниме) — локальная
настройка на устройстве, общая колода фильтруется у каждого своя; ручные
предложения партнёра показываются всегда. Нужен ли фильтр в первой
версии — вопрос §12.

**Добавить** и **Совпало** — без изменений (D3).

## 12. Открытые вопросы владельцу

1. **Источник:** берём Викиданные (CC0, «топ» по числу статей в Википедиях,
   а не по оценкам зрителей)? Или проект считается некоммерческим и стоит
   смотреть TMDB (атрибуция, кэш ≤ 6 мес., ключ у оператора)?
2. **Состав топа:** квоты 900 фильмов / 300 сериалов / 150 мультфильмов /
   150 аниме — так? Нужен ли перекос в русскоязычное/советское кино (у
   Викиданных популярность «мировая»)?
3. **Порог:** N = 5 совпадений и ≥ 20 голосов у каждого — ок?
4. **Обновление каталога:** только с релизами (asset) или ещё
   Go-эндпоинт, раздающий один файл всем?
5. **«Уже смотрели»:** нужен ли третий ответ, кроме да/нет? Это новое
   значение `vote` (3) той же длины; в модели вкуса «смотрели» ≈ слабое «да».
6. **Фильтр видов** на «Выборе» — в первой версии или позже?
7. **Постеры** — хотлинк Кинопоиска, как сейчас в поиске, ок для каталога
   (тысячи картинок)? Альтернатива — без постера, если нет на Commons.
8. **Описание** у Викиданных короткое («фильм 2001 года»). Хватит, или
   показывать только жанры/страну/год?
