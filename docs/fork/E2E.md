# E2E в Tethered: модель угроз и дизайн (S7)

Статус: **принят** (2026-10-21). Решения владельца — в §12, по ним
поправлены §6.2, §6.3, §7, §9 и §10. Код E2E — S8, S9.

## 1. Что хотим получить

Сервер хранит и пересылает шифртекст и минимум метаданных. Прочитать
переписку, воспоминания, геопозицию, цикл и прочее содержимое пары может только
устройство участника пары. Подменить ключ незаметно сервер не может.

Не цели:

- скрыть сам факт общения, кто с кем в паре и когда что-то писал (метаданные
  остаются, §4);
- защита от вредоносного кода на телефоне участника или от участника, который
  сам пересылает содержимое;
- анонимность от оператора на уровне сети (IP видит Caddy).

## 2. Модель угроз

| Противник | Что может | Что получает в форке с E2E | Как защищаемся |
|---|---|---|---|
| **Честно-любопытный сервер** (оператор читает базу и логи) | Читать всё в SQLite, бэкапах, Centrifugo | Шифртекст, метаданные §4 | Шифрование содержимого на клиенте; ключи пары не покидают устройства в открытом виде |
| **Изъятие или взлом сервера** | То же плюс бэкапы за всё время | То же | Как выше; бэкапы ключей (§7) зашифрованы ключом от фразы восстановления, которой у сервера нет |
| **Активный MITM со стороны сервера** при обмене ключами | Подменить открытый ключ участника или устройства | Ничего, если пользователи сверили эмодзи или прошли по QR/ссылке | PSK из фрагмента ссылки (§6.2), сверка эмодзи с коммитментом и полный отпечаток в QR (§6.3), подписанный список устройств (§5.2) |
| **Украденный телефон** | Доступ к разблокированному устройству или к его памяти | Всё, что видит владелец, если телефон разблокирован | Ключи в Keystore; офлайн-кэш уже зашифрован (AUDIT §1); PIN приложения — отдельная задача, не E2E |
| **Бывший партнёр** после выхода из пары | Ключ пары, который у него был | Прошлое содержимое (уже видел); новое — нет | Ротация ключа пары при выходе участника (§6.5) |

Отдельно о **Centrifugo**: он часть сервера, через него идут только
шифрованные события (те же записи) и эфемерные сообщения клиента
(`typing`, `alive`, штрихи рисунка, точки геопозиции), которые клиент тоже
шифрует ключом пары (§8).

## 3. Криптографические примитивы

Только libsodium, своей криптографии нет.

| Назначение | Примитив |
|---|---|
| Ключ пары, шифрование записей | `crypto_aead_xchacha20poly1305_ietf` (ключ 32 байта, nonce 24 случайных) |
| Файлы (фото, видео, голос, кружки) | `crypto_secretstream_xchacha20poly1305`, чанки 64 КиБ |
| Доставка ключа пары устройству | `crypto_box_seal` (X25519) |
| Подписи (список устройств, приглашение) | `crypto_sign` (Ed25519) |
| Ключи из фразы или пароля | `crypto_pwhash` Argon2id (§7) |
| Отпечатки, вывод ключей и эмодзи сверки | `crypto_generichash` (BLAKE2b, с ключом и контекстом) |
| Общий секрет сверки (§6.3) | `crypto_kx` (X25519 + BLAKE2b, эфемерные ключи) |
| MAC подтверждения в приглашении | `crypto_auth` (HMAC-SHA512-256) |

Обёртка для Flutter — **`sodium`** (FFI к libsodium; сам собирает её из
исходников хуком сборки — `sodium_libs` устарел; полная сборка, с secretstream,
sealed box и Argon2id). У `cryptography` нет secretstream и sealed box, а
Argon2id на чистом Dart медленный для разумных параметров. Проверено в S8: release APK
содержит `libsodium.so` под arm64, тесты гоняют настоящую libsodium на хосте.

## 4. Классификация данных

Принцип форка (PLAN «Принципы»): схема апстрима ложится на нашу без смены
смысла полей. Строковые и JSON-поля шифруются **на месте** (`e2e1.…`, §8):
так правка одного поля остаётся правкой одного поля. Где поле не строка и не
JSON (числа, даты), содержимое переезжает в новое поле `enc`, а старое
пустеет.

### Шифруется

| Коллекция | Что уходит в `enc` |
|---|---|
| `chat_messages` | `text`, `reply_to_text`, `reply_to_name`, `reactions`, `pin_title`, `pin_thumb`, `voice_url`/`note_url` (ссылки на зашифрованные файлы + их ключи), `voice_peaks`, `note_thumb`, `face`, `color`… — всё, кроме служебных полей ниже |
| `memories` | весь `data` (тип, текст, медиа, место, музыка, книги, фильмы, капсула — §9) |
| `memory_comments` | текст |
| `mood_entries` | настроение, заметка |
| `cycle_entries` | все данные цикла |
| `live_location` | `data` (координаты, точность, батарея) |
| `wishes`, `wish_categories`, `wish_reservations` | названия, описания, ссылки, цены |
| `canvas_strokes`, `canvas_meta`, `canvas_catalogue` | штрихи, вставки, названия |
| `miss_you`, `miss_you_events` | `text`, последний импульс |
| `custom_moods` | подпись и картинка (файл) |
| `love_tests` | ответы |
| `widget_data` | содержимое виджетов (фото партнёра, заметка, статус) |
| `groups` | `member_moods`, `member_ailments`, `current_status`, `custom_statuses`, `member_birthdays`, `start_date`, `anniversary_date`, `first_kiss_date`, `timers`, `custom_relationship_*`, `placeholder_name` |
| `media` | файлы целиком (secretstream); превью — отдельным зашифрованным файлом |
| `watch_videos`, `watch_history` | ссылки на ролики и названия |

### Остаётся открытым (метаданные)

- id записей, `group_id`/`pair_id`, автор (`user_uid`/`author_uid`), время
  создания и правки — без них не работают правила доступа, синхронизация по
  `updated` и рассылка по каналам.
- Состав пары (`groups.members`), счётчики (`messages_count`,
  `memories_count`…), стрики, монеты и сундуки — игровая механика сервера.
- Тип записи там, где по нему работает сервер (`kind` в `media`: аватар или
  нет — от этого зависят правила).
- Размеры файлов (с точностью до чанка) и частота сообщений.
- Профиль пользователя (`display_name`, аватар) — виден партнёру через
  `/api/user/card`; шифровать его ключом пары нельзя, у человека может быть
  несколько пар. Открытым считаем осознанно.

## 5. Ключи

### 5.1 Какие ключи есть

| Ключ | Где живёт | Зачем |
|---|---|---|
| **Ключ аккаунта** `AK` (Ed25519) | На каждом устройстве человека (Keystore), в бэкапе (§7) | Подписывает список устройств аккаунта. Его отпечаток — то, что сверяют партнёры |
| **Ключ устройства** `DK` (X25519 + Ed25519) | Только на устройстве, Keystore | Получать ключи пар (sealed box), подписывать свои события |
| **Ключ пары** `PK_e` (32 байта, эпоха `e`) | На устройствах участников, в бэкапе | Шифрует содержимое пары |
| **Ключ файла** `FK` (32 байта, случайный) | Внутри зашифрованной записи | Шифрует один файл |

### 5.2 Список устройств аккаунта

Сервер хранит коллекцию `e2e_identities` (S8): ключ аккаунта и подписанный им
**список устройств** `{user, version, devices:[{id, box, sign, kind}], sig_AK}`;
версию списка сервер двигает только вперёд. Выданные ключи пары —
`e2e_grants`, шаги приглашения и сверки — `e2e_handshake`, бэкап ключей —
`e2e_backups`. Клиент партнёра
принимает устройство, только если оно есть в подписанном списке с
неубывающей версией. Сервер не может ни добавить своё устройство (нет `AK`),
ни откатить список (версия).

Новое устройство человека получает `AK` и ключи пар одним из двух путей:

1. **связка со старым устройством**: QR на новом → старое проверяет и
   шифрует `AK` и ключи пар под `DK` нового (sealed box);
2. **восстановление из бэкапа** (§7).

Каждое добавление устройства партнёр видит строкой в чате: «у Алисы новое
устройство» (как в Signal). Код безопасности (§6.3) от этого не меняется: он
считается от `AK`.

## 6. Пара

### 6.1 Создание ключа пары

Ключ `PK_1` генерирует приглашающий в момент выпуска кода. Пока второго
участника нет, ключ есть только у его устройств.

### 6.2 Приём приглашения

Приглашение у апстрима — 6 символов кода, ссылка `https://…/invite/CODE` и QR
`tethered://invite/CODE`. Код продиктовать можно, а секрет в 6 символах не
передать, поэтому два уровня:

**Ссылка или QR (проверено автоматически).** Приглашающий кладёт во
**фрагмент** ссылки `#s=<секрет 32 байта>&f=<отпечаток AK>`. Фрагмент не уходит
на сервер ни браузером, ни приложением.

1. Принимающий получает от сервера `AK`-отпечаток приглашающего вместе с
   ответом `/api/invite/accept` и сверяет с `f` из фрагмента.
2. Принимающий публикует свой подписанный список устройств и
   `MAC_s(свой AK pub ‖ список устройств)`.
3. Приглашающий проверяет MAC: без `s` сервер его не подделает. Только после
   этого он шифрует `PK_1` под ключи устройств принимающего.
4. Пара помечается «проверено».

**Только код (продиктован).** Сервер может подменить ключи, поэтому пара
помечается «не проверено», обмен ключом идёт как выше, но без шага MAC. Пара
работает полностью, но в чате и на экране пары висит заметная плашка
«ключи не проверены — сверьте эмодзи» (решение §12.4). После сверки (§6.3) —
«проверено».

Итого три пути:

| Как связались | Статус |
|---|---|
| Ссылка или QR из приложения | проверено сразу |
| Продиктованный код + сверка эмодзи по голосу (§6.3) | проверено |
| Только продиктованный код | не проверено, с плашкой |

### 6.3 Сверка ключей: эмодзи и QR

Короткий статический код от двух ключей (`hash(AK_a ‖ AK_b)` → 12 цифр,
~40 бит) не годится: сервер-MITM подставляет ключи сам и может перебирать
их, пока коды у двух сторон не совпадут, — это парадокс дней рождения,
~2²¹ попыток. Поэтому два способа:

**Эмодзи (голосом, по созвону).** Схема Matrix SAS (`m.sas.v1`):

1. Оба открывают экран «сверить ключи». A генерирует эфемерный X25519 `e_A` и
   публикует только коммитмент `C = BLAKE2b(e_A pub ‖ AK_a ‖ AK_b)`.
2. B публикует `e_B pub`.
3. A раскрывает `e_A pub`, B проверяет коммитмент.
4. Оба считают общий секрет `S` (`crypto_kx`) и
   `SAS = BLAKE2b(ключ = S, «tethered-sas-v1» ‖ AK_a ‖ AK_b ‖ e_A pub ‖ e_B pub)`.
5. Первые 42 бита → 7 эмодзи из таблицы Matrix (64 эмодзи по 6 бит, с
   утверждёнными названиями и переводами — их удобно диктовать).
6. Партнёры называют эмодзи друг другу и жмут «совпадает». По желанию
   (настройка) B не сравнивает, а набирает продиктованные эмодзи с сетки 64 —
   от привычки жать «да» не глядя.
7. При совпадении каждый подписывает своим `AK` `AK` партнёра; пара
   «проверено».

Коммитмент лишает сервер перебора: к моменту, когда он видит `e_A`, свой
`e_B` он уже выбрал. Одна попытка подмены, шанс 2⁻⁴² (1 к 4·10¹²). Длина
SAS на скорость шифрования данных не влияет: она нужна только при сверке.

**QR (вживую).** Полный отпечаток `BLAKE2b(min(AK) ‖ max(AK))`, 256 бит;
сканируют друг у друга, перебор невозможен.

Смена `AK` партнёра (переустановка без бэкапа) сбрасывает статус в
«не проверено» и показывается в чате.

### 6.4 Пары больше двух

Схема апстрима допускает `max_members > 2`. Ключ пары шифруется под каждое
устройство каждого участника; код безопасности считается попарно с каждым.

### 6.5 Ротация

Новая эпоха `PK_{e+1}` при: выходе участника, удалении устройства из списка,
подозрении на компрометацию (вручную). Новое шифруется новой эпохой, старое
остаётся под старой (у оставшихся есть все эпохи). Ушедший партнёр читает
только то, что было до его ухода.

Ещё новая эпоха — после сверки, снявшей «ключ сменился» или «подмену»: старый
ключ мог уйти на устройство, которое подсунул сервер. Эпоху создаёт участник
с наименьшим uid (иначе двое создали бы разные эпохи с одним номером),
остальные просят его шагом `rotate_request`. Партнёру с пометкой «подмена»
ключи пары не выдаются, пока сверка её не снимет.

Повторное перешифрование старого контента ротацию не делает: ушедший его уже
видел, а перешифровать гигабайты медиа на телефоне — дорого.

## 7. Восстановление

Без бэкапа потеря телефона = потеря истории. Поэтому при первом входе
предлагаем (настойчиво) включить бэкап ключей:

- **Фраза восстановления**: 24 слова (256 бит) из списка BIP39, показывается
  один раз. Ключ бэкапа `BK = Argon2id(фраза, соль)` — энтропии достаточно,
  Argon2id здесь ради единообразия и защиты от ошибок.
- **Пароль** (по выбору вместо фразы): `BK = Argon2id(пароль, соль,
  opslimit=MODERATE, memlimit=256 МиБ)`. Сервер может перебирать пароль
  офлайн, поэтому требования жёсткие и проверяются на устройстве (решение
  §12.1):
  - не короче 12 символов, строчные и заглавные буквы, цифра и символ;
  - нет в словаре утёкших паролей: топ-300k (SecLists Pwdb) в фильтре Блума
    внутри APK (202 КБ, ложных срабатываний 0,1 %), без запросов в чужие
    сервисы; сравниваются и сам пароль, и его основа — без регистра, цифр и
    символов по краям, с обратными leet-заменами (`P@ssw0rd2024!` → `password`);
  - не содержит email или имя, нет повторов (`aaaa`, `1234`) и раскладочных
    последовательностей (`qwerty`, `йцукен`);
  - при отказе объясняем причину, а не просто «слабый».

На сервере лежит `e2e_backups`: `{user, method, kdf: {salt, ops, mem}, nonce,
enc(AK, ключи всех пар всех эпох)}`. Устройство хранит выведенный ключ бэкапа
`BK` (не фразу и не пароль) и перешифровывает бэкап при каждом новом ключе
пары. Параметры Argon2id приходят с сервера при восстановлении — клиент не
берёт память больше 1 ГиБ.

Новый телефон без ключей, но с бэкапом на сервере: приложение не создаёт
ключи само, а просит фразу или пароль. Восстановленный ключ аккаунта тот же —
партнёр не видит смены ключа, новое устройство добавляется в список. Без
фразы — «начать заново»: новый ключ аккаунта, партнёр видит «ключ сменился».

## 8. Конверт

```json
{
  "enc_v": 1,
  "alg": "xchacha20poly1305-ietf",
  "key_id": "<group_id>:<эпоха>",
  "nonce": "<base64url, 24 байта>",
  "ct": "<base64url>"
}
```

- AAD = `enc_v ‖ коллекция ‖ id записи ‖ поле ‖ key_id`. Сервер не может
  переложить шифртекст в другую запись, другое поле или другую пару.
- Внутри `ct` — JSON с полями, которые раньше лежали открыто.
- **Текстовые поля записей шифруются на месте** (S9, `record_codec.dart`):
  в колонке лежит `e2e1.<key_id>.<nonce>.<ct>`, AAD тот же, `ct` — UTF-8
  самого поля. Поле за полем, а не одним `enc` на запись: правка шлёт только
  изменённые колонки, а очередь офлайна собирает её без остальных полей.
  Какие поля каких коллекций шифруются — `e2eFields`; JSON-поля (`reactions`)
  шифруются так же, строкой. Числа и флаги остаются открытыми — по ним
  фильтрует и сортирует сервер. Предел длины шифруемых
  полей на сервере поднят до 32000 символов (миграция
  `1760000003_e2e_sealed_fields`).
- Поля, которые на месте не зашифровать (даты), переезжают в текстовое
  поле `enc` записи, а в колонке остаётся одно значение на всех: у отметки
  цикла `day` — `2000-01-01` (колонка обязательная). По датам отметок цикл
  читается и без их типа, поэтому дата тоже прячется. Без ключа отметка
  уезжает на ту же дату, за пределы календаря, а не в «сегодня».
- Геопозиция: `live_location.data` — JSON на месте; `group_id` у записи нет,
  пара находится по составу канала `pair_<a>_<b>`. Живые точки в канале
  `loc:<канал>` идут конвертом канала, AAD — канал, `point:<uid автора>` и
  время точки: сервер не выдаст точку одного за точку другого.
- Шифрует и расшифровывает HTTP-клиент PocketBase (`E2EHttpClient`) и разбор
  дельт Centrifugo — две точки, через которые записи входят в приложение и
  выходят из него. Офлайн-кэш, очередь и экраны видят открытый текст; кэш
  сам зашифрован на устройстве. Поле, которое не открылось (ключ эпохи ещё
  не пришёл), показывается заглушкой «🔒», шифртекст остаётся в
  `e2e_locked` и открывается, когда ключ придёт.
- Пока главный сервис E2E не поднялся (первые секунды запуска, фоновый
  изолят уведомлений), ключи читаются из Keystore только на чтение: очередь
  не уходит открытым текстом, а уведомление из фона показывает текст.
- Эфемерные сообщения Centrifugo (`typing`, `alive`, штрихи, точки) — тот же
  конверт, AAD = `канал ‖ тип сообщения ‖ время`.
- Версия `enc_v` растёт при смене формата; клиент читает все известные версии.

## 9. Капсула времени

Ключ капсулы делится на две части (решение §12.2):

- содержимое (текст и файлы) шифруется случайным `CK = K1 ⊕ K2`;
- `K1` лежит в `enc` записи под ключом пары;
- `K2` открыто отдаётся серверу, тот прячет его до `openAt` тем же
  механизмом, что до E2E прятал всё содержимое (S6);
- автор хранит `CK` целиком у себя (и в бэкапе ключей §7) и может открыть
  свою капсулу в любой момент.

Сервер видит только `K2` и прочитать не может; партнёр до срока видит только
`K1` и тоже не может. Открыть раньше можно лишь сговором сервера и партнёра.
Сервер ничего не перешифровывает — медиа капсулы не трогаются. Открыто
остаются дата открытия, факт капсулы и размер. Риск: потерянный `K2` делает
капсулу нечитаемой для партнёра — его закрывают бэкапы сервера (S10).

## 10. Что ломается на сервере и чем заменяется

| Сейчас на сервере | После E2E |
|---|---|
| Поиск по чату (`text ~` в фильтре PocketBase) | Клиент листает историю пары страницами по 200 (до 10 000 сообщений за запрос экрана) и ищет у себя (`ForkChatSearch`). Вкладки без текста — голосовые, кружки, воспоминания — по-прежнему ищет сервер |
| Превью ссылок (`/api/link/preview`) | Клиент сам решает: через meta gateway (сервер видит ссылку, но не связывает её с сообщением) или напрямую с устройства (настройка, PLAN S5) |
| Раскадровка «живого фото» для виджета (`widget_anim`, `tools/widget_anim.py`) | На телефоне (ffmpeg-kit или нативный MediaMetadataRetriever); если дорого — отключить живые фото в виджете |
| Превью воспоминаний (`memory_thumbs.py`, `thumb_cache.py`) | Клиент делает превью и шифрует отдельным файлом |
| Статистика пары (`/api/couple/stats` считает настроения) | Клиент из своих данных |
| Зеркало дней рождения в `groups.member_birthdays` (хук `birthdays`) | Шифруется ключом пары, хук убирается |
| Текст уведомлений | Уже на клиенте (`PbPushService`), просто расшифровывает |
| Модерация, жалобы | Нет доступа к содержимому; жалоба отправляет копию сама |
| Веб-страница комнаты «Смотрим вместе» (`pb_public/watch`) | Чат комнаты — E2E на ключе сессии, §10.1. Ролики и их ссылки — открыто, голос и так DTLS-SRTP между участниками (§12.3) |

### 10.1 Веб-комната: ключ на сессию

Сейчас комната в приложении — WebView со страницей с сервера; страница сама
сидит в канале Centrifugo и грузит `youtube.com/iframe_api` в свой контекст.
JS страницы отдаёт сервер, а скрипт YouTube видит всё, что видит страница.
Поэтому:

- **в приложении ключи и чат — нативные.** Канал `watch:<room>` держит
  приложение (`WatchChannel` уже говорит на протоколе комнаты), шифрует и
  расшифровывает. Чат — нативный оверлей поверх WebView, как панель голоса.
  WebView — только плеер: получает от приложения `load/play/pause/seek`,
  отдаёт состояние; к Centrifugo не подключается, ключей и текста чата не
  видит. Подменённая сервером страница узнает ссылку на ролик и позицию —
  их и так не шифруем;
- **ключ сессии `RK`** — 32 случайных байта, создаёт первый участник,
  открывший комнату; живёт только в памяти и стирается с концом сессии.
  Следующая сессия — новый `RK`. С ключами пары и аккаунта `RK` не связан:
  не выводится из них и не хранится под ними. Между приложениями `RK` идёт
  по E2E-каналу пары (`crypto_box_seal` на ключи устройств из подписанного
  списка, §5.2) — без QR и без ключей в ссылках;
- **браузер на компьютере** (партнёр без приложения): весь JS там с
  сервера, честного E2E не будет. Видео и голос работают, чат идёт открытым
  текстом с пометкой в комнате «в браузере переписка видна серверу»
  (решение §12.3). Пока в комнате есть браузер, приложения тоже пишут в чат
  открыто и показывают ту же пометку;
- сервер (апстрим так и устроен) не хранит ни комнат, ни переписки: история
  канала Centrifugo выключена.

## 11. Миграция (S9)

1. Клиент новой версии читает и шифрованные, и открытые поля, а пишет
   шифрованные, как только у пары есть ключ (двойное чтение). Пока ключа нет
   (партнёр ещё не обменялся ключами) — пишет открыто, плашка в чате об этом
   говорит.
2. Фоновая миграция на устройстве: каждый перешифровывает **свои** старые
   записи — чужие править не даёт сервер (`chat_guard.pb.js`). Запускается при
   открытии пары, когда есть ключ; ищет записи с открытыми полями фильтром
   `поле !~ 'e2e1.'`, так что прогресс хранить негде и незачем.
3. Отметки прогресса на сервере нет: повторный запуск находит только то,
   что ещё не перешифровано.
4. Проверка (S9, тест CI): дамп SQLite и перехват публикаций Centrifugo не
   содержат маркеров открытого текста из тестовых данных.
5. Порядок по возрастанию риска: чат → геопозиция и цикл → воспоминания и
   медиа → поля `groups`, желания, рисунки, капсулы (PLAN S9).

## 12. Решения владельца (2026-10-21)

1. **Бэкап ключей**: и фраза, и пароль. Пароль — с жёсткими требованиями и
   проверкой по словарю утечек на устройстве (§7).
2. **Капсула**: защищаемся прежде всего от сервера, но и партнёру раньше
   срока не открыть — ключ делится между парой и сервером (§9). Дата остаётся
   открытой.
3. **Веб-комната**: в приложении чат и ключи нативные, WebView только
   играет; ключ на каждую сессию, не связанный с ключами пары, идёт по
   E2E-каналу. В браузере на компьютере чат открытый с пометкой «в браузере
   переписка видна серверу». Ролики не шифруются, голос и так шифрован
   (§10.1). Прокси роликов — отдельно, PLAN S11.
4. **Пара по продиктованному коду**: работает в статусе «не проверено» с
   заметной плашкой. Сверка — эмодзи по голосу (7 из 64, схема Matrix с
   коммитментом) или QR (§6.3).
