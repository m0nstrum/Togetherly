# План форка: self-hosted + E2E

Контекст и находки собраны в [AUDIT.md](AUDIT.md). Каждая сессия начинается с
чтения обоих файлов, а заканчивается обновлением раздела «Статус» внизу.

## Цели

1. **Полный self-hosted.** Клиент не обращается ни к одному адресу автора. Внешние
   сервисы вызываются только через наш сервер и только там, где без них не обойтись.
2. **Без телеметрии и мусорных SDK.** Убрать рекламу, аналитику, обязательный
   крашрепортинг и RuStore.
3. **Воспроизводимый бэкенд.** Поднимается одной командой. Включает и то, чего нет в
   репозитории апстрима.
4. **E2E для чувствительных данных.** Сервер хранит шифртекст и минимум метаданных.
5. **Остаёмся мёржабельными с апстримом.** Продуктовые фичи автора подтягиваем, а не
   переписываем.

Пока не делаем: свои тайлы карты. В сессии 1 адрес тайлов только выносится в
конфиг.

## Принципы работы с апстримом

- Remote `upstream` = `THET1ME-1/togetherly`. Апстрим регулярно **мёржим**
  (не ребейзим) в `main` форка.
- Код форка кладём в **новые файлы**: `lib/fork/…` на клиенте, отдельный `server/`
  на бэкенде. Чужие файлы правим точечно, через шов (вызов, флаг, адаптер).
- Каждую правку чужого файла записываем в `docs/fork/TOUCHPOINTS.md`: файл, зачем,
  как разрешать конфликт. По этому реестру проходит каждый мёрж апстрима.
- Удаляем через флаги сборки и заглушки, а не через массовое удаление кода. Так
  меньше конфликтов. Мёртвый код удаляем только когда он мешает.
- E2E по определению ломает протокольную совместимость с сервером апстрима. Чтобы
  схема апстрима ложилась на нашу, шифртекст пишем в **новые поля**
  (`enc`, `enc_v`), а не меняем смысл старых.

## Ключевые решения (предложение, подтвердить в сессии 0)

### БД: PocketBase на SQLite, PocketBase как Go-библиотека. Без Postgres и hotpath

- Клиент говорит на API PocketBase. `hotpath` повторяет тот же API, поэтому
  возврат на чистый PB клиент не заметит.
- Узким местом у автора была цепочка JS-хуков (JSVM) на пути записи при его
  нагрузке. У self-hosted инстанса на несколько пар такой нагрузки нет.
- PocketBase подключаем как Go-фреймворк (`pocketbase.New()` + свои хуки и роуты
  на Go). Получаем один бинарник, типизированную логику и тесты на `testing`.
  JS-хуки переносим постепенно: на первом этапе их можно запускать как есть.
- SQLite в WAL, бэкап через `litestream` или снапшоты PB.
- Если упрёмся в производительность, перенесём горячие хуки в Go. К Postgres
  вернёмся только по факту замеров.
- Таблицы, которые живут только в `hotpath` (`pocketbase/hotpath/*.sql`:
  `cycle_wishes`, `love_mascots`, `miss_you_events`, `movies_cache`, `note_fields`…),
  становятся миграциями PB.

### Realtime: оставляем Centrifugo

Клиент и Android push (WebSocket в foreground-сервисе) завязаны на него. Свой
SSE в PocketBase потребовал бы переписать клиент. Centrifugo тоже один бинарник.

### Внешние сервисы: «meta gateway» на нашем сервере

Все метаданные (oEmbed, музыка, книги, фильмы, превью ссылок) клиент запрашивает
у нашего сервера. Сервер обращается к провайдеру и кэширует ответ. Провайдер видит
IP сервера, а не пользователя.

Компромисс: сервер видит саму ссылку, которую резолвит. Чтобы это обойти, сделаем
настройку «резолвить напрямую с устройства».

### Push

Только Android. Основной путь — **FCM своего Firebase-проекта как будильник**
(решение 22.10.2026, S12): сервер шлёт data-сообщение без содержимого
(«есть событие»), телефон просыпается, сам забирает данные со своего сервера
и расшифровывает. Запасной путь — Centrifugo WS в foreground-сервисе, как
сейчас: без Google Play Services или без настроенного Firebase. Сервер
содержимое уведомлений не формирует.

### Крипто: libsodium

Обёртка для Flutter: `sodium_libs` или `cryptography`, выбрать в S7. Самописной
криптографии не будет.

## Сессии

Сессии идут по порядку, кроме отмеченных «параллельно». Размер сессии подобран
так, чтобы результат можно было запушить и проверить.

### S0. Инфраструктура форка

- `upstream` remote, политика веток (`main`, фича-ветки), `TOUCHPOINTS.md`.
- **Своя идентичность приложения**: applicationId/bundle id, имя, ключ подписи,
  URL-схемы (`loveapp://`, `togetherlyrustore://`). Без этого сборка форка
  конфликтует с приложением апстрима на устройстве и в App Links.
- CI: `flutter analyze`, `flutter test`, сборка APK. Проверить, что тесты апстрима
  вообще зелёные, и зафиксировать базовую линию.
- Закрыть оставшиеся «Открытые вопросы» (крашрепорты, идентичность форка).
- **Готово, когда:** CI зелёный на чистом форке, решения записаны в этот файл.

### S1. Вынос конфигурации

- `lib/fork/config/endpoints.dart`: единая точка для всех адресов через
  `--dart-define` или файл (`--dart-define-from-file=env/<name>.json`). У значений
  нет дефолтов на прод автора: обязательное значение отсутствует — сборка или
  старт падает с понятной ошибкой.
- Перевести на неё всё из AUDIT §3: PB, Centrifugo, games, siteHost, инвайт-ссылки,
  белый список медиа-хостов, legal-URL, релизы, тайлы карты, music meta.
- App Links / Universal Links: хосты подставляются из конфига (Gradle
  `manifestPlaceholders`, xcconfig для entitlements). Брошенные домены уходят.
- Тест-сторож: grep-тест в CI падает, если в `lib/`, `android/` или `ios/` появляется
  `togetherly.day`, `duckdns`, `web.app` или IP-литерал. Это ловит новые хардкоды
  при мёржах апстрима.
- **Готово, когда:** сторож зелёный, приложение собирается под тестовый конфиг.

### S2. Телеметрия и SDK (можно параллельно с S1)

- Sentry: перевести на свой Bugsink по решению 6 (DSN из конфига, opt-in, без PII).
- `AnalyticsService`: заглушка без сети. Вызовы в экранах остаются, чтобы не трогать
  чужие файлы.
- Убрать AdMob и Yandex Ads: флаг сборки плюс no-op реализации рекламных сервисов.
  Убрать сами зависимости из `pubspec.yaml` (одна точка касания), вычистить
  манифест и Info.plist (ad app id, SKAdNetwork, ATT).
- Убрать RuStore SDK, reels-прокси (`169.58.6.158`) и хвосты Firebase, включая
  FCM: `firebase-messaging`/`play-services-base` в Gradle, `FcmService.kt`,
  канал `love_app/fcm`, `users.fcm_token` (см. AUDIT §3).
- Монетизацию (монеты, сундуки, IAP, Plus, lava, донаты) обработать по решению из
  «Открытых вопросов».
- Проверка: собрать release, посмотреть зависимости (`flutter pub deps`, merged
  manifest) и снять сетевой трафик эмулятора через mitmproxy. Ни одного запроса
  мимо наших хостов.
- **Готово, когда:** в трафике release-сборки только наши хосты (тайлы карты пока
  исключение).

### S3. Инвентаризация API бэкенда

Без этой сессии воссоздание сервера превратится в гадание.

- Собрать полную карту того, что вызывает клиент:
  - коллекции и поля (из Dart-моделей, а не только из `collections_schema.json`);
  - роуты `/api/*`;
  - каналы Centrifugo;
  - формы ответов.
- Сопоставить карту с `pb_hooks`, `hotpath.py` и `*.sql`. Отметить то, чего в
  репозитории нет (link_fetcher, modapi, и т.д.).
- Каждый пункт пометить: переносим / переписываем / выкидываем
  (монетизация и т.п., по решению S0).
- Внешние сервисы: список провайдеров, кто их вызывает (клиент или сервер), чем
  заменяем.
- **Результат:** `docs/fork/API_INVENTORY.md`, по нему пишутся тесты паритета.

### S4. Бэкенд, часть 1: каркас

- Каталог `server/`: Go-модуль, PocketBase как библиотека, слои
  domain/usecase/handler/infrastructure, `slog`, конфиг из env (koanf).
- Миграции: коллекции из `collections_schema.json` и таблицы из `hotpath/*.sql`.
  Правила доступа описаны кодом в одном месте. Расхождение `apply_acl.py` и схемы
  (AUDIT §2) разрешаем здесь.
- `deploy/`: `docker-compose` с сервисами server, Centrifugo, Caddy (Caddyfile в
  репозитории) и coturn, бэкап SQLite. Почта через свой SMTP вместо Gmail.
- Тесты правил доступа: чужой пользователь не читает и не пишет ни одну коллекцию
  пары. Здесь же проверяем гипотезу про `live_location`.
- **Готово, когда:** `docker compose up`, клиент из S1 логинится, создаёт пару,
  пишет в чат.

### S5. Бэкенд, часть 2: паритет

- Перенести роуты и хуки по `API_INVENTORY`: инвайты, группы, waiting,
  draw/reels-инвайты, watch-комнаты, coturn-креды, счётчики, стрики, Centrifugo-токены, медиа.
- Meta gateway: oEmbed, музыка, книги, фильмы, превью ссылок. Безопасный fetcher
  (без SSRF и с повторной проверкой адреса на редиректах), кэш. Клиент переводим на
  gateway.
- Тесты паритета: прогон сценариев против нашего сервера. Пригодятся и тесты автора
  (`pocketbase/*.test.py`, `pb_hooks/*.test.js`).
- **Готово, когда:** основные сценарии из инвентаря проходят, клиент не ходит к
  сторонним API напрямую.

### S6. Срочные фиксы безопасности (можно параллельно с S4 и S5)

- `live_location`: канал привязан к группе автора записи.
- Токен сессии хранить в `flutter_secure_storage`.
- Удалить отправку через APNs (`push_apns.pb.js`, `apns_push.js`).
- Капсула: сервер не отдаёт `data` до даты открытия. До E2E это закрывается на
  сервере, после — половиной ключа, которую сервер выдаёт по времени (E2E.md §9).
- `user_presence` и аватары читают только члены пары.

### S7. E2E: дизайн и модель угроз (только документ, можно параллельно с S3–S6)

- Модель угроз:
  - честно-любопытный сервер;
  - изъятие или взлом сервера;
  - активный MITM со стороны сервера при обмене ключами;
  - украденный телефон;
  - бывший партнёр после выхода из пары.
- Классификация данных: что шифруем, что остаётся метаданными и почему. Кандидаты на
  шифрование:
  - чат (текст, ответы, голосовые, кружки);
  - live-локация;
  - цикл;
  - воспоминания и медиа;
  - настроения, болезни, даты в `groups`;
  - желания;
  - рисунки;
  - капсулы.
- Ключи:
  - ключи устройства (X25519 + Ed25519);
  - ключ пары (XChaCha20-Poly1305);
  - обмен при приёме инвайта с проверкой отпечатка через QR или фрагмент ссылки
    (`#…`, который сервер не видит);
  - сверка «кодом безопасности» в UI.
- Несколько устройств, восстановление (recovery-фраза и/или бэкап ключа под
  паролем с Argon2id), ротация при выходе участника, группы больше двух.
- Медиа: шифрование файла потоком (secretstream), превью шифруются отдельно.
- Что ломается на сервере (AUDIT §1) и чем это заменяется. Поиск по чату переходит
  на клиент (локальный индекс в зашифрованном кэше).
- Формат конверта `{enc_v, alg, key_id, nonce, ct}` и версионирование.
- **Готово, когда:** документ `docs/fork/E2E.md` прошёл ревью. Без этого код E2E не
  пишем.

### S8. E2E: ядро

- `lib/fork/e2e/`: обёртка libsodium, хранилище ключей (Keychain/Keystore), конверт,
  тест-векторы.
- Обмен ключами в флоу инвайта, экран кода безопасности, recovery.
- Сервер: коллекция публичных ключей устройств, раздача обёрнутых ключей пары.
  Сервер не должен уметь подменить ключ незаметно.
- **Готово, когда:** две тестовые установки получают общий ключ пары, и подмену
  ключа на сервере видно в UI.

### S9. E2E: данные, по возрастанию риска

1. Чат: адаптер в слое данных шифрует перед отправкой и расшифровывает после
   получения. Поиск идёт локально.
2. Live-локация и цикл.
3. Воспоминания, медиа, превью. Серверные обложки и превью переезжают на клиент.
4. Поля `groups`, желания, рисунки, капсулы.

На каждом шаге: двойное чтение (открытое и зашифрованное), фоновая миграция старых
записей, проверка, что в БД и в Centrifugo не осталось открытого текста. Проверка
сделана тестом: дамп БД + grep по маркерам.

### S10. Эксплуатация и выпуск

- Шифрованные бэкапы, восстановление из бэкапа (проверить на деле).
- Свой мониторинг без телеметрии пользователей: метрики сервера в Prometheus.
- Обновить политику конфиденциальности под реальное поведение форка.
- Чек-лист мёржа апстрима: TOUCHPOINTS, сторож хостов, тесты паритета, тест на
  отсутствие открытого текста.

### S11. Прокси роликов «Смотрим вместе» (после E2E, опционально)

YouTube в РФ не работает, у Vimeo бывают проблемы. Smart DNS и SNI-прокси не
помогают: ТСПУ режет по SNI в открытом ClientHello, куда бы ни вёл DNS.
Поэтому прокси на уровне приложения:

- WebView комнаты получает прокси через `ProxyController` (androidx.webkit):
  HTTPS-соединение до нашего сервера, DPI видит только TLS к нашему домену.
- Сервер — CONNECT-прокси с белым списком доменов (`youtube.com`,
  `googlevideo.com`, `ytimg.com`, `vimeo.com`…) и входом по токену
  пользователя. TLS до источника сквозной, без MITM: сервер видит домены, не
  ролики. Плеер остаётся родным, извлекать потоки (yt-dlp) не нужно.
- Включает оператор флагом, по умолчанию выключено: трафик роликов идёт через
  VPS, а в РФ это может подпадать под запрет средств обхода блокировок
  (149-ФЗ, ст. 15.8) — решает оператор.
- Лимиты трафика на пару, метрики объёма без доменов и ссылок.
- Проверить на деле: пускает ли YouTube воспроизведение с IP дата-центра.
- Браузер на компьютере прокси не получает — только приложение.
- **Готово, когда:** ролик YouTube играет в комнате с телефона, у которого
  YouTube заблокирован, а с выключенным флагом прокси не принимает соединений.

### S12. FCM как будильник (решение 22.10.2026)

Фоновый сервис с сокетом убивают энергосбережение и прошивки — уведомления
опаздывают или теряются. FCM доставляет надёжнее, а приватность сохраняем
тем, что через Google не идёт ничего, кроме факта события.

- **Firebase-проект свой** (оператора инстанса), без Analytics, Android-приложение
  `io.github.m0nstrum.tethered`. Ни Google Sign-In, ни SHA-1, ни публикация в
  Google Play не нужны. FCM бесплатный.
- **Клиент:** вернуть избирательно нативный `FcmService.kt` апстрима (без
  `firebase_messaging` и прочей инфраструктуры Google апстрима), регистрацию
  в `AndroidManifest.xml`, мост `love_app/fcm` к `lib/services/fcm_service.dart`
  (он сохранился). `google-services.json` — при сборке, вне репозитория; без
  него сборка идёт без FCM (как сейчас).
- **Сервер:** токены устройств в своей коллекции (только владелец); отправка
  через FCM HTTP v1 сервисным аккаунтом оператора (`TETHERED_FCM__*`; пусто —
  выключено). Повод — те же события, по которым сейчас будит сокет: новое
  сообщение, «скучаю», зов в рисование/ленты и т. п.
- **Что уходит в Google:** только `{type: "sync", event: <id>}` с
  `priority: HIGH`. Ни текста, ни имён, ни координат, ни id пары. Телефон
  показывает уведомление сам: забирает событие со своего сервера,
  расшифровывает и рисует текст. Не успел или нечем — нейтральное «Новое
  сообщение» (high-priority data без видимого уведомления FCM со временем
  понижает в приоритете).
- **Запасной путь:** нет Google Play Services, Firebase не настроен или FCM не
  поднялся — остаётся foreground-сервис с Centrifugo.
- **Готово, когда:** приложение выгружено из памяти, телефон в доке —
  сообщение партнёра приходит уведомлением с текстом; в журнале сервера и в
  запросе к FCM нет ничего, кроме id события.

## Принятые решения (21.10.2026)

1. **Монетизация: всё бесплатно.**
   - Клиент: все платные фичи разблокированы локально.
   - Удаляем IAP, Plus, lava, донаты, кошелёк, рекламу за награду.
   - Монеты и сундуки как игровую механику без денег оставляем, только если их
     удаление ломает UI. Решаем в S3 по инвентарю.
   - Сервер: не переносим `iap_*`, `lava*`, `donations`, `income`, `plus_*`,
     `wallet_*`, `apple_*`, `redeem`.
2. **iOS не нужен.**
   - Из плана уходят APNs, NSE, Apple Sign-In и App Store.
   - Каталог `ios/` не удаляем (иначе будут конфликты при мёржах апстрима), просто
     не собираем.
   - Push только через Centrifugo WS в foreground-сервисе Android.
3. **Вход только по почте и паролю.** Убираем Google Sign-In и OAuth-провайдеры.
   Нужны свой SMTP для подтверждения почты и сброса пароля и защита от перебора.
4. **TikTok-ленты, «Смотрим вместе» и игры нужны.** Что это требует:
   - **Игры:** сами игры не переносим (исходников `games.togetherly.day` в
     репозитории нет). Оставляем только точку расширения: адрес каталога игр
     задаётся в конфиге (`GAMES_URL`), пустой адрес скрывает вход в UI
     (`watch_home_screen.dart:366`). Контракт «как встраивается игра» описываем в S3,
     чтобы игры можно было добавить позже.
   - **«Смотрим вместе»:** WebRTC, поэтому в compose нужен coturn
     (`pb_hooks/watch_rtc.pb.js`). Убрать STUN Google (`stun.l.google.com`) и
     оставить только свой. Веб-часть берём из `pocketbase/pb_public/watch`.
   - **TikTok:** из РФ его страницы закрыты, нужен прокси. Делаем свой, опционально,
     адрес в конфиге. Пользователь при этом обращается к TikTok напрямую, это
     осознанное исключение из правила «только наши хосты». YouTube, Rutube и прочие
     встраивания — то же самое: мы не контролируем, что они собирают.
5. **Масштаб: до 100 пар.** SQLite хватает с большим запасом. Hotpath и Postgres не
   переносим, их таблицы становятся миграциями PocketBase.

6. **Крашрепорты нужны.** Свой Bugsink: один контейнер на SQLite, совместим с
   Sentry, поэтому `sentry_flutter` в клиенте остаётся.
   - DSN берётся из конфига; без DSN отправка выключена.
   - Отправка только с согласия пользователя: переключатель в настройках и вопрос
     при первом запуске.
   - `user.id` не отправляется, `sendDefaultPii = false`.
   - Breadcrumbs и контексты чистятся в `beforeSend`: никаких текстов, URL с
     токенами и координат.
   - Bugsink включаем в compose как опциональный сервис.
7. **Имя форка: Tethered.**
   - applicationId: `io.github.m0nstrum.tethered`. Это уникальное имя пакета для
     Android, а не адрес сервера; к хосту, где разворачивается инстанс, оно не
     привязано.
   - URL-схема: `tethered://`.
   - В S0 нужны своя иконка и свой ключ подписи.
   - Ключ подписи храним вне репозитория.

8. **Решения 22.10.2026.**
   - **Монеты и сундуки** — игровая механика без денег (так уже и работает:
     хуки `coins`/`chest`, траты на темы и фоны; всё, что за деньги, —
     выкинуто). **Публичный профиль пары** (`profile_web`) выкинут: хук в
     сервер не попадает, веб-оболочка `shell`, единственный его потребитель,
     тоже. API_INVENTORY §9 закрыт.
   - **Даты пары** (`start_date`, `anniversary_date`) шифруются: «дни вместе» и
     годовщину телефон считает сам по расшифрованной записи пары, серверу они
     не нужны. Экран статистики берёт даты из записи пары, а не из
     `/api/couple/stats`. Остальные цифры этого экрана в форке и сейчас
     нулевые — их считал hotpath апстрима; перенос подсчёта на телефон —
     отдельной задачей.
   - **«Ленты вдвоём»** — так же, как «Смотрим вместе»: чат в приложении на
     ключе сессии, страница только показывает ролики (S9, §10.1 E2E.md).
   - **iPhone** — пока не занимаемся (нативное окно комнаты, локальный прокси
     медиа без `NSAllowsLocalNetworking`).
   - **FCM возвращаем как будильник** (S12): свой Firebase-проект, через
     Google идёт только «есть событие», без текста, имён и координат.
