# Tethered: отделение от апстрима

Решение 24.10.2026: Tethered перестаёт быть форком Togetherly. Апстрим больше
не мёржим, бренд — Tethered, приложение перерабатываем по частям, не переписывая
с нуля. Текущий `docs/history/PLAN.md` закрываем как историю этапа форка.

## Лицензии

| Часть | Лицензия | Почему |
|---|---|---|
| Приложение (Flutter, страницы комнаты) | GPL-3.0, исходники открыты | Производная от Togetherly. Копирайт автора в унаследованных файлах сохраняем; в «О приложении» — «основано на Togetherly (GPL-3.0)». |
| Сервер (Go) | своя, на выбор владельца | Наш код. Условие — ни строчки апстрима внутри: JS-хуки апстрима переносим в Go (этап 2) и удаляем. До этого сервер не распространяем. |
| Протокол (API, формат E2E) | описан открыто | Открытый клиент обязан уметь с ним работать. |

Монетизация — позже и только на стороне сервера/сервиса. Клиент под GPL
остаётся бесплатным и открытым.

## Этап 1. Добить бренд Tethered (несколько дней)

`applicationId`, схема диплинков и домен (через env при сборке) уже свои. Остаётся:

1. Остатки «Togetherly» в видимых текстах, справке, ассетах; маскоты и стикеры апстрима оставляем (функции держим), но проверяем лицензию ассетов.
2. Внутренние имена: Kotlin-namespace `com.togetherly.love`, `love_app` в Dart-пакете, `loveapp://` во внутренних payload уведомлений — переименовать без смены `applicationId` (пользователям ничего не переустанавливать).
3. iOS: bundle id, App Group виджетов, схема ссылок — на те же параметры из env, что у Android.
4. «О приложении»: версия, лицензия GPL-3.0, ссылка на исходники, «основано на Togetherly».
5. Справка, политика конфиденциальности, контакты — свои.

Готово, когда: собранный APK не содержит строк и ассетов апстрима (проверка скриптом в CI).

## Этап 2. Сервер целиком на Go (2–4 недели)

Цель: вся логика — наш код в clean architecture, PocketBase — хранилище и вход.

1. Перенос JS-хуков в Go (domain/usecase/handler/infrastructure), по одному с живым тестом на каждый:
   группы (patch-map, leave, record-activity, miss-you), инвайты и ожидание пары, токены Centrifugo, карточка пользователя, счётчики, стражи, push, комната просмотра.
2. Модель доступа «через операции»: общие записи (группа, настройки пары) меняются только роутами; прямой PATCH коллекций закрыт правилами. Стражи из JS исчезают как класс.
3. Единые ошибки и коды ответов, валидация, лимиты, slog, метрики/трейсинг на каждом роуте.
4. Миграции схемы — только Go; чистка мёртвых коллекций апстрима.
5. Вынос сервера в отдельный репозиторий со своей лицензией (после пункта 1).
6. Решение: оставаться на PocketBase или переходить на чистый Postgres + sqlc. Принимается в конце этапа по фактам (нагрузка, удобство миграций).

Готово, когда: `pocketbase/pb_hooks` не участвует в сборке, все тесты хуков — Go-тесты.

## Этап 3. Клиент по слоям (постепенно, месяцы)

Правило: экран переписывается, когда в нём всё равно предстоит работа. Никаких «больших переписываний» ради переписывания.

1. Слой данных: репозитории по фичам вместо `PbDataService`; одна офлайн-очередь с типизированными операциями; E2E прозрачно в репозитории.
2. Состояние: единый подход (Riverpod или аналог) вместо россыпи синглтонов и `setState` на тысячи строк.
3. Порядок экранов: чат → главная → профиль пары → настройки → остальное.
4. Дизайн-система Tethered: токены, компоненты, доступность (48 dp, TalkBack, крупный шрифт) — уже наработанные «кирпичи» `ForkFailure`/`ForkNotice` становятся её частью.
5. Каждый переписанный экран — с тестами и без зависимостей на старый слой.

## Этап 4. Продукт

1. Функции апстрима пока держим все (решение 24.10). Ревизия — по мере переработки экранов, список утверждает владелец.
2. Свои функции дальше по бэклогу (`docs/history/PLAN.md`, хвост M-пунктов и UI-находок переносится сюда).
3. Монетизация — отдельное решение позже; только серверные возможности, без замков в открытом клиенте.

## Порядок и зависимости

```
Этап 0 ──► Этап 1 ──► Этап 3 (по ходу работы)
   └─────► Этап 2 ──► вынос сервера в свой репозиторий
Этап 4 — решения владельца, параллельно
```

Этапы 1 и 2 независимы и могут идти параллельно после этапа 0.
